One recommendation, staged deliberately

Static linking is not the problem. Go already compiles and caches packages independently. The immediate problem is that hundreds of command implementations and tests share one package boundary.

1. Evaluate cohesive libraries

Review the three boundaries, then approve one medium-complexity, more-coupled pilot. Reuse existing narrow provider interfaces; inject clocks/process inputs when useful. Real temporary files are acceptable; avoid blanket effects abstractions or one package per command.

Observed
Cheaper independently runnable focused tests in three pilots.
Cost
API, navigation, and fixtures; benefits must earn these per boundary.

2. Keep one executable

The composition root wires libraries into the stable CLI. Retain unrelated tests, whole-command integration, and current required PR gates. Proposed affected-package CI needs representative edit-test and actual CI critical-path/runner-cost evidence before claiming savings or relaxing gates.

Gain
Current installation, signing, update, rollback, and cross-platform simplicity.
Cost
A production patch still replaces the whole executable.

3. Preserve the option to externalize

Keep package APIs explicit and free of package-main state; do not force transport neutrality or hypothetical host needs. A separate wire/host and deployment compatibility design needs named patch or fault-isolation value and independent approval.

Option
Independently patchable, isolated capabilities if justified; not demonstrated by these pilots.
Cost
Future IPC, compatibility, signing, lifecycle, and rollback work requires separate approval.

Explicit exclusions

No native Go plugins, reflective DI container, loose adjacent files, PATH discovery, per-file hot replacement, or general long-lived RPC platform.

Why
Preserves Windows support and avoids accidental loader and lifecycle complexity.
Tradeoff
Third-party in-process extensibility is not a goal of this architecture.

Migration sequence

Only individually approved issues activate implementation. Review prototypes, select the exact next candidate, and measure before broader migration. Passing a prototype gate is not production approval.

Phase 0: capture the selected candidate's contracts

Preserve dated evidence; capture outputs, errors, provider behavior, flags, aliases, result files, and environment per candidate, not all commands upfront. Exit: recorded baseline and conformance fixtures with explicit coverage limits; no runtime component behavior.

Phase 1: review three boundaries and one representative pilot

Approve the exact medium-complexity, more-coupled candidate. Use ordinary APIs and retained integration checks in one binary. Exit: measured per-candidate stop/go gate below plus representative edit-test results and team cost acceptance.

Conditional Phase 2: selective source/test expansion

Broader family migration requires the pilot gate and team approval. Extract registry metadata or a common linked contract only for demonstrated repeated shared needs. Exit: every approved boundary preserves behavior and earns its cost; no mandatory common framework.

Optional Phase 3: prove an external host

Separate approval for named patch or fault-isolation value and a deployment compatibility design. Exit: demonstrated value and linked/subprocess parity; otherwise stop with linked libraries.

Optional Phase 4: component-set delivery

Signed manifest, safe paths, atomic activation, retention, and rollback. Exit: unchanged gaggles, demonstrated patch/isolation value, validated skew, draining, recovery, and deployment compatibility; CI gain is a separate claim.

Optional Phase 5: selective expansion

Other stage families only with evidence; Portal/content packs only for demonstrated independent patch value. Long-lived read workers need measured justification; engine/runner/journal extraction is not an assumed destination.

Per-candidate stop/go gate: preserve CLI, output, results, errors, provider behavior, and existing integration checks; add useful independently runnable tests; reduce production dependency closure by at least 50% and warm go test -count=1 -run '^$' overhead by at least 25% against that candidate's own baseline. These are prototype criteria, not universal product goals. API, navigation, and fixture costs must remain modest and accepted by the team. Report noise and representative edit-test results. Stop or revise on failure; retaining better tests without extraction is valid. Numerical success alone is not approval.

Guardrails

Stable CLI commands, aliases, flags, help, outputs/results/errors, provider behavior, gaggle YAML, and GOOBERS_BIN remain unchanged. Retain schemas, offline validation, recovery, and the supported platform contract. This source refactor changes no dispatcher version-skew checks, upgrade/draining behavior, binary deployment unit, or cloud rolling-upgrade guarantees. Future external components require separate deployment compatibility design. The host controls below are deferred reference design, not activated work.

Goobers architecture decision package

Smaller validation boundaries. Safe hot patches. One stable CLI.

The current Goobers executable is a 103 MiB statically linked product with a highly concentrated command package. The concrete recommendation is to turn built-ins into layered, independently testable Go libraries now, while defining host-neutral package contracts. External process hosting remains an optional later decision, not a prerequisite for the refactor.

The measured shape

The dominant issue is package and test concentration, not embedded file size. Runtime splitting alone would not remove the existing CI long pole.

5.10MiB raw embedded payloads
CI already divides cmd/goobers into three test pieces because package-level sharding cannot split it. This is evidence for source ownership changes before deployment changes. Unit tests exist today, but package-main coupling, globals, broad construction, and shared fixtures make them harder to isolate and schedule than normal Go package tests.
Why this is worth doing: moving files and tests is mechanical and can be automated. The durable payoff is better coverage, reliability, diagnosability, and comprehensibility, plus faster local and CI validation. Those benefits remain even if Goobers always ships as one executable.

Recommended architecture

The public executable owns compatibility and recovery. Built-ins are linked libraries behind one capability registry; a future host boundary can move a selected library out of process without changing the public contract.

One recommendation, staged deliberately

Static linking is not the problem. Go already compiles and caches packages independently. The immediate problem is that hundreds of command implementations and tests share one package boundary.

1. Layer built-ins as libraries

Move command families, tests, fixtures, schemas, and descriptors out of package main. Inject providers, journals, clocks, filesystems, and process effects explicitly.

Gain
Focused local unit tests, package-level CI scheduling, clearer dependency direction.
Cost
Large source and test migration; boundaries must be enforced.

2. Keep one executable initially

The thin composition root wires libraries into the stable CLI. CI builds the complete executable for registry, schema, composition, and end-to-end gates.

Gain
Current installation, signing, update, rollback, and cross-platform simplicity.
Cost
A production patch still replaces the whole executable.

3. Preserve the option to externalize

Keep library APIs free of package-main state and transport assumptions. Add a wire protocol only after a named capability demonstrates patch or isolation value.

Gain
A real route to independently patchable, process-isolated capabilities.
Cost
None of the IPC cost is paid unless the optional host is approved.

Explicit exclusions

No native Go plugins, reflective DI container, loose adjacent files, PATH discovery, per-file hot replacement, or general long-lived RPC platform.

Why
Preserves Windows support and avoids accidental loader and lifecycle complexity.
Tradeoff
Third-party in-process extensibility is not a goal of this architecture.

Migration sequence

Each phase is independently useful and has a rollback point. Runtime complexity is introduced only after the source boundary is proven.

Freeze contracts and measurements

Inventory command outputs, flags, result files, environment, and current CI costs.

Decompose source and tests

Extract command families from package main while still linking one executable.

Define the linked capability contract

Separate descriptors from implementations without introducing an IPC protocol.

Optional: prove an external host

Only for a capability with demonstrated patch or isolation value; stop if the benefit is insufficient.

Optional: build component-set delivery

Signed manifest, safe paths, atomic activation, retention, and rollback for the proven helper.

Expand only with evidence

Other stage families first; Portal and content packs only for demonstrated independent patch value.

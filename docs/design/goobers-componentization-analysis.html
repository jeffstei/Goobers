Goobers architecture decision package

Smaller validation boundaries. Safe hot patches. One stable CLI.

The current Goobers executable is a 103 MiB statically linked product with a highly concentrated command package. The recommended path is not DLLs or Go plugins: decompose source and tests first, then add signed component sets and private helper processes behind the unchanged goobers entry point.

Full recommendation Boundary inventory Measured evidence
Decision: phased hybrid. Keep validation fallback, daemon, engine, journal, update, and recovery in the core. Trial component activation with Portal assets, then extract deterministic workflow-stage commands to a private one-shot helper. Existing gaggles continue to invoke goobers <command>.

Migration sequence

Each phase is independently useful and has a rollback point. Runtime complexity is introduced only after the source boundary is proven.

Freeze contracts and measurements

Inventory command outputs, flags, result files, environment, and current CI costs.

Decompose source and tests

Extract command families from package main while still linking one executable.

Build component-set foundation

Signed manifest, safe paths, immutable staging, atomic activation, health, retention, rollback.

Trial external Portal

Use the existing fs.FS seam and retain an embedded compatible fallback.

Extract deterministic stage helper

Delegate a small command family through the existing argv/env/result-file contract.

Expand only with evidence

Other stage families and content packs next; long-lived workers only for measured need.
